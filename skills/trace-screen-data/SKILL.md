# trace-screen-data — 화면 값 추적 · 대조 점검

PinProof 익스텐션과 함께 쓰는 선택 스킬이다(패널에서 프로젝트에 설치하거나 개인 설정에 직접 둔다). PinProof 가 «어느 화면의 어떤 값이 이상한지» 를 증거로 남긴다면, 이 스킬은 그 값이 **원천과 산식까지 따라가도 맞는지** 를 판정한다. `.pinproof/` 가 없어도 동작한다(화면 전수 점검).

## 0. 원칙

- **검토 전용.** 코드 · 설정 · 커밋 · PR/MR · 이슈 생성을 이 스킬 안에서 하지 않는다. 산출물은 이슈 초안 목록이다.
  찾는 쪽이 고치기까지 하면 «지금 바로 고칠 수 있는 것» 으로 발견이 좁아진다. 수정은 승인 뒤 별도 작업(`/pinproof` 처리 등)으로 넘긴다.
- **판정 기준은 «깨져 보이는가» 가 아니라 «그 값이 맞는가».** 화면의 숫자 · 상태 · 등급 · 점수마다 원천까지 추적한다.
- **이미 고친 항목도 제외하지 않는다.** 최근 커밋으로 고쳤다는 항목은 «재검증» 으로 다시 본다.
- **커버리지를 증명한다.** «발견 없음» 은 인벤토리 표에서 그 화면 · 탭 · 권한을 실제로 봤다는 근거와 함께만 쓴다.
- **PinProof 항목은 읽기만 한다.** `.pinproof/items/*.md` 의 `status` · `sent` · `## 처리 기록` 을 바꾸지 않는다. 처리 표시는 `/pinproof` 의 몫이다.

## 1. 입력 · 범위 확정

### 인자

| 인자 | 범위 |
|---|---|
| 없음 | `.pinproof/` 가 있으면 대기 항목을 카테고리별로 보여 주고, 전체 화면 점검으로 갈지 특정 카테고리로 좁힐지 한 번 묻는다. 없으면 전체 화면 점검 |
| 카테고리 이름(예: `데이터 정합성`) | 그 카테고리의 대기 항목을 출발점으로, 같은 데이터 개념을 쓰는 다른 화면까지 넓혀 본다 |
| 항목 번호(예: `13 14`) | 그 항목들을 출발점으로 같은 방식으로 넓혀 본다 |
| 화면 · 경로 · 메뉴 이름 | 그 화면들만 |

### PinProof 항목 찾기

- 지금 폴더에 `.pinproof/` 가 없으면 `git worktree list` 첫 줄(메인 워크트리)의 `.pinproof/` 를 읽는다. 코드 확인은 지금 폴더에서 한다.
- 대기 항목: `.pinproof/items/NNN.md` 중 frontmatter `status: 대기`. 보관함(`items/archive/`)은 사용자가 번호로 집을 때만 본다.
- 항목에서 쓰는 단서: 메모, 페이지 주소 · route, selector, 화면 글자, 컴포넌트 · 소스 위치(`src/...:줄`), 테이블 헤더 · 보이는 행 수, 네트워크 기록(메서드 · URL · 상태 · 응답 앞 500자), 스크린샷(`items/assets/NNN.png`).
- `env: deployed` 항목은 배포 빌드에서 담긴 것이다. 소스 위치가 비거나 압축돼 있을 수 있으니 화면 글자 · selector · API 경로로 코드를 찾고, **배포 버전과 지금 코드의 차이를 먼저 확인**한다.
- PinProof 는 값을 원본 그대로만 담는다(파싱 · 집계 · 비교 안 함). 테이블의 «보이는 행 수» 는 가상 스크롤 때문에 전체가 아닐 수 있다 — 개수 판단은 반드시 데이터 출처로 한다.

### 환경 (사용자가 따로 정하지 않으면 코드에서 찾아 바로 진행)

| 항목 | 정하는 법 |
|---|---|
| 화면 목록 | 라우터 설정 · 메뉴 정의 · 페이지 디렉터리에서 찾는다. 탭 · 드로어 · 모달 · 행 클릭 이동 · 딥링크 전용 상세를 포함한다 |
| 권한 · 계정 | 역할(관리자 · 운영자 · 일반 사용자 등)이 코드에 있으면 역할별로 본다. 로그인 정보는 사용자가 준 것만 쓰고, 없으면 코드 경로로 판정한다 |
| 실행 환경 | 로컬 개발 서버 주소를 찾고, 떠 있는 서버의 빌드가 지금 코드와 같은지(시작 시각 ↔ `git log`) 확인해 적는다 |
| 공유 · 배포 환경 | 사용자가 지정할 때만. **읽기 전용**: 저장 · 삭제 · 발송 버튼은 누르지 않는다(대화상자까지만). 응답 속도는 판정에서 뺀다 |
| 원천 접근 | DB · 로그 · 외부 API 를 읽을 수 있으면 조회만 한다(SELECT · GET · 읽기 전용 클라이언트). 접근 정보가 없으면 묻거나 코드 경로로 판정한다 |

로컬에서 재현되지 않는 상태(조회 실패 · 빈 데이터 · 목록 상한 초과 · 외부 시스템 꺼짐 등)는 **«못 본 것» 이 아니라 «잠재» 판정 대상**이다 — 코드 경로를 추적해 판정한다.

## 2. 인벤토리

화면마다 한 줄로 아래 사슬을 만든다. 산출: 스크래치 파일 `inventory.md`(스크래치패드가 있으면 그곳, 없으면 임시 폴더 — 프로젝트 안에 남기지 않는다).

```
화면 · 경로 → 컴포넌트(라우터 → 페이지 파일)
  → 탭 · 모달 · 드로어 · 이동 링크
  → 호출 API(프런트 API 모듈의 endpoint)
  → 서버 핸들러(파일:줄)
  → 원천(DB 테이블 · 컬럼 / 캐시 / 외부 시스템)
  → 산식(집계 · 변환 · 판정 함수)
```

- PinProof 항목에서 출발했으면 항목 번호를 그 줄에 붙인다(`#13`).
- 서버 라우트 중 **어느 화면에서도 호출이 보이지 않는 API** 를 따로 적는다(동적 경로로 닿음 / 화면 없는 기능).
- 화면 증거가 필요하면 브라우저 자동화(Playwright 등)로 권한별 스크린샷 · 실패 API · 콘솔 오류를 디스크에 남긴다. 이것은 입력일 뿐 판정 근거의 전부가 아니다.

## 3. 분할 — 메뉴가 아니라 데이터 개념 단위

메뉴로 나누면 여러 화면에 걸친 모순(예: 같은 «건수» 가 화면마다 다른 분모를 씀)이 사이로 빠진다.
서브에이전트를 쓸 수 있고 화면이 많으면 아래처럼 나눠 맡긴다(6명 이내). 작은 앱이면 혼자 같은 순서로 본다.

| 담당 | 맡는 것 |
|---|---|
| 개념별 1~3명 | 앱의 핵심 데이터 개념별로 — 예: 주문 · 매출 / 사용자 · 권한 / 재고 · 수량 / 알림 · 이벤트 · 기간 |
| 교차 대조 1명 | 같은 개념이 여러 화면 · 보고서 · 내보내기에 나올 때 값 · 정의 · 등급 · 이름이 같은지 |
| 권한 범위 1명 | 같은 API 를 역할별로 불러 비교 — 보여선 안 될 데이터, 비워야 할 필드, 소속 범위 |
| 보기 결함 1명(선택) | 넘침 · 잘림 · NaN · 미번역 키 · 가로 스크롤. 사용자가 원할 때만 |

- 맡길 때는 아래 4절 브리프를 스크래치 파일 `audit-brief.md` 로 써서 경로를 넘기고, 대화에 담당 · 범위를 적는다.
- PinProof 항목은 그 개념을 맡은 담당에게 함께 넘긴다.

## 4. 점검 브리프 (공통 지침)

1. **읽기 전용.** 파일 수정 금지, 셸은 조회만. 라이브 대조도 읽기만.
2. **값마다 사슬 추적.** 화면에 보이는 숫자 · 상태 · 등급 하나마다 «API 응답 필드 → 서버 핸들러/서비스 → 쿼리 · 원천 컬럼 → 산식» 을 적고, 아래를 확인한다.
   - 단위: 초당 vs 주기당 · 바이트 원값 · % 와 비율 · ms/s · 통화 · 소수 자릿수
   - 집계: 시간 창 · 분모(전체 vs 잘린 목록 길이 · 현재 페이지) · 반올림 · 중복 행 · 삭제/취소 건 포함 여부
   - 시간: 표시 시간대 변환 경유 여부 · UTC 날짜 경계 · 미래 시각 · «오늘 / 최근 N일» 의 시작점
   - 부재: 조회 실패 · 미측정 · 0 · 빈 목록이 화면에서 구분되는가(실패를 0 이나 «없음» 으로 그리지 않는가)
   - 잘림: LIMIT · 페이지 상한이 있을 때 «전체» 로 표기하지 않는가, 잘림을 알리는가
   - 판정: 상태 분류가 정본 함수를 지나는가, 대소문자 · 알 수 없는 값 처리
   - 의미: 라벨 · 도움말 · 툴팁이 실제 산식과 맞는가. 고정값 · 휴리스틱을 «정상» · «확정» 으로 서술하지 않는가
   - 범위: 사용자 소속 · 역할에 따라 응답이 맞게 좁혀지는가
3. **판정 어휘.** 실재(오늘 틀리게 보이거나 동작) / 잠재(오늘 데이터로는 미도달 — 코드 경로로 판정) / 서식(동작 무관).
   심각도: 상 = 사용자가 틀린 판단을 하게 만드는 수치 · 상태, 또는 기능 불능 / 중 = 오해 소지 · 정보 손실 / 하 = 보기 결함.
4. **증거.** 항목마다 `파일:줄` + (API 응답 발췌 또는 쿼리 결과). PinProof 항목이 있으면 그 번호와 항목 속 증거(네트워크 응답 · 화면 글자)를 함께. grep 0건을 근거로 쓰면 그 grep 이 유효함을 보이는 히트를 같이 적는다. 토큰 · 비밀번호 · 개인정보는 출력하지 않는다.
5. **출력 형식.**
   ```
   ## 발견
   | ID | 판정·심각도 | 화면(메뉴 > 페이지 > 탭) · 권한 | PinProof 항목 | 증상 | 사슬(화면 → API → 원천 → 산식) | 근거 | 서버 수정 Y/N |
   ## 확인했고 문제없음 — 화면 · 탭 · 권한별로 본 값
   ## 못 본 것 — 사유(캡처 실패 · 원천 접근 불가 · 판단 보류)
   ```
6. **금지.** 근거 없는 추측, 새 기능 제안, 취향 제안. 커버리지 공백은 반드시 «못 본 것» 에 적는다.

## 5. 검증

- **상 등급 전부 + 중 등급 일부**를 반증하려고 다시 본다: API 원문을 직접 부르고, 원천 쿼리를 다시 돌리고, 같은 값이 나오는 다른 화면을 연다.
- 떠 있는 서버가 낡은 빌드면 서버 응답 차이는 코드로 판정한다.
- 같은 원인의 발견은 하나로 묶는다(이슈 하나 = 원인 하나). PinProof 항목 여러 개가 한 원인이면 번호를 모두 적는다.
- 열린 이슈와 겹치는지 확인한다(`gh issue list --search` · `glab issue list --search` 중 쓸 수 있는 것, `git log --oneline -S '<심볼>'`). 겹치면 이슈 번호를 적는다.

## 6. 보고

1. 첫 줄: 실재 상 N · 중 N · 하 N, 잠재 N, 서식 N.
2. **커버리지 표**: 화면 수 × 권한 수 × 본 탭 수, «못 본 것» 수. PinProof 항목에서 출발했으면 항목별로 «원인 확인 / 문제없음 / 못 봄».
3. **발견 표**: 4절 형식 + 기존 이슈 겹침 칸. 상 등급은 왜 문제인지 한 줄씩.
4. **이슈 초안 목록**: 제목 · 근거 · 우선순위 · 결정이 필요한 항목은 따로 표시.
5. 마지막 줄: 다음 단계를 묻는다 — 이슈로 만들지, PinProof 항목이면 `/pinproof <번호>` 로 처리할지. 승인한 것만 진행한다.

## 하지 말 것

- 이 스킬 안에서 코드 수정 · 커밋 · push · PR/MR · 머지 · 이슈 생성.
- `.pinproof/` 항목의 상태 · 넘김 표시 · 처리 기록 수정, 항목 파일 생성 · 삭제.
- 한 권한(관리자 등)만 보고 끝내기.
- 메뉴 단위로만 나누기(교차 대조 없이).
- 스크린샷이 정상으로 보인다는 이유로 수치를 «문제없음» 처리하기.
- 공유 · 배포 환경에서 쓰기 동작.
